# Bounded improvement

Use the appropriate entry below and perform its authorized operations. Do not stop at advice or a blank worksheet. This skill grants no authority to change code, publish, install or weaken constraints. It uses existing actors, tools and records; no tracker, companion skill or runtime is required.

## A. Actual closure

Verify the actual Issue/PR closure through its current source, including cancelled and unmerged closures. Do not fabricate a closure to exercise the skill. A deferred open item or updated report is not a closure event.

Read the original goal, cumulative outcome, closure reason, applicable guidance, necessary evidence and unfinished obligations. Identify the responsible closure owner and authorized save location. Find any prior retrospective using stable work identity and verified relationships. Matching titles alone do not justify deduplication.

For another closure of the same work unit, reference the previous account and add only materially new outcomes. Preserve distinct events and failures in related Issues/PRs; reopening does not erase earlier evidence. Do not count a PR's Issue representation, merge and close as three independent work units.

Produce the smallest useful retrospective in the existing review/closure record: outcome, supported causes, competing explanations, whether current guidance already covered and was followed, then a justified reversible change, no change or deferral. For adoption, identify authority, applicability, owner, next actual use, validation, failure and rollback conditions.

Save through the authorized existing tool and read back the actual content and link. Reconcile an uncertain write before retrying. If saving is unavailable, return the full account with the specific persistence gap. Do not close a parent or invent a new task because a retrospective was saved.

At the next comparable use, observe the actual action and result and save/read back that application account. Keep lesson stored, later use observed, application account saved and benefit demonstrated as four different claims. Existing guidance being sufficient is a valid reason not to add anything.

## B. Improvement-method experiment

Use this entry only when the assigned outcome is to improve how improvements are generated, diagnosed, compared or selected. It may start from a real demonstrated failure without pretending that a still-open Issue closed. Improving a task output or correcting a completion label alone is not recursive method improvement.

Use [the experiment worksheet](templates/method-experiment.md) only for material facts; equivalent existing prose is valid. Preserve the actual current mechanism M0 and exact candidate M1. Identify what operation in candidate generation or evaluation changes and why evidence supports trying it. Do not deliberately weaken M0 to produce a win.

Before execution, freeze comparable inputs and tools, observable success criteria, legitimate positive behavior, non-regression limits, cost bounds, rollback and stop conditions. Separate development examples from held-out cases when claiming generalization. A fixture must really construct the claimed condition. Preserve failed or inconclusive results; do not silently retune the standard.

Run the authorized candidate method on a real improvement opportunity and inspect actual decisions/actions and outputs. Compare against M0 under the recorded conditions, including confounders and costs. Adopt, reject, defer or roll back based on evidence. No change and inconclusive evidence are valid; observed use alone is not benefit. A candidate cannot grant itself permissions or rewrite its original objective.

After a bounded adoption or explicitly bounded trial, observe whether M1 actually participates in generating or evaluating a subsequent improvement-method candidate M2. Record which method was loaded, inputs, actual evaluation and disposition. Do not preselect a passing M2 or call an unchanged external process's second proposal recursion. M2 can be rejected; without the actual link it remains unobserved.

## Return and stop

Return the inspected evidence, decisions, actual effects, storage/readback, applicable method identity, costs, failures and remaining obligations through the existing record. Attribute user corrections honestly. Report recurrence separately from comparative benefit; a finite M0/M1/M2 chain does not establish sustained acceleration or general RSI.

Stop or roll back the affected experiment at its justified evidence, budget, safety or authority boundary. Do not recursively create review tasks for every report update. Retain outstanding validation/rollback owners if this skill is removed. Automatic coverage extends only to closure events actually delivered by the host; this package is not a background listener.
